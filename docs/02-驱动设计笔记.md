# 02 - 驱动设计笔记（字符设备 / I2C / 中断 / 设备树）

> 对照 `driver/sensor_char.c` 阅读。全文按"一个字符设备驱动如何与 I2C 传感器、中断、设备树协作"来组织。

---

## 0. 整体数据流

```
                 ┌──────────────────── 用户态 ────────────────────┐
                 │  sensor_test: open/read/ioctl/write            │
                 └───────────────┬───────────────────────────────┘
                                 │ 系统调用（copy_to_user / copy_from_user）
┌────────────────────────────────▼──────────────────────────────────┐
│                          内核态                                    │
│  file_operations:  sensor_open / sensor_read / sensor_ioctl ...    │
│         │                                  ▲                       │
│         │ 读缓存                           │ wake_up_interruptible │
│         ▼                                  │                       │
│   sd->latest (struct sensor_sample) ── waitqueue (sd->wq)          │
│         ▲                                                          │
│         │ 写入采样结果                                              │
│  sensor_irq_thread()  ← 线程化下半部（可睡眠）                       │
│         ▲                                                          │
│         │ 唤醒线程                                                  │
│  sensor_irq_hard()    ← 上半部（不可睡眠，只登记）                    │
│         ▲                                                          │
│         │ generic_handle_domain_irq(sd->irq_domain, 0)              │
│  sensor_timer_fn()    ← hrtimer 周期触发（模拟传感器 DRDY 引脚）       │
│                                                                    │
│  I2C 子系统:  i2c_get_adapter(0) → i2c_new_client_device()          │
│               i2c_smbus_read_word_data(client, 0x00)                │
│         ▲                                                          │
│  platform_driver.probe()  ← of_match_table 匹配 dts 的 compatible   │
└────────────────────────────────┬───────────────────────────────────┘
                                 │
                    QEMU 模拟的 I2C 总线（i2c-stub 虚拟 0x48 从设备）
```

## 1. 字符设备：设备号、cdev、file_operations

### 1.1 主次设备号

| 名称 | 含义 | 本项目 |
|------|------|--------|
| 主设备号 (major) | 标识"哪个驱动" | 511（`alloc_chrdev_region` 动态分配） |
| 次设备号 (minor) | 标识"驱动管理的第几个设备" | 0 → `/dev/sensor0` |

```c
alloc_chrdev_region(&sd->devt, 0, 1, DRV_NAME);   /* 动态申请，内核给号 */
// 也可以固定：register_chrdev_region(MKDEV(major,0), 1, DRV_NAME);
```
> 查看：`cat /proc/devices`（按主设备号列出），`ls -l /dev/sensor0` 看 `511, 0`。

### 1.2 注册三步曲

```c
cdev_init(&sd->cdev, &sensor_fops);      /* 1. 把 fops 绑到 cdev */
sd->cdev.owner = THIS_MODULE;
cdev_add(&sd->cdev, sd->devt, 1);        /* 2. 加入内核字符设备表 */

sd->char_dev = device_create(sensor_class, NULL, sd->devt, sd,
                             "sensor%d", MINOR(sd->devt));  /* 3. 在 /dev 下建节点 */
```
第 3 步配合内核的 **devtmpfs**（`CONFIG_DEVTMPFS_MOUNT=y`）会自动创建 `/dev/sensor0`；
没有 devtmpfs 的老系统需要手动 `mknod /dev/sensor0 c 511 0` 或依赖 udev。
`class_create()` 还会在 `/sys/class/sensor_char/sensor0/` 下暴露属性（可写自定义 sysfs 属性）。

### 1.3 file_operations 每个回调干什么

| 回调 | 本驱动实现 | 要点 |
|------|-----------|------|
| `.open` | 计数 + 打印 | 设备已被 `cdev_add` 绑定到 inode，用 `inode->i_cdev` 反查私有结构 |
| `.read` | **阻塞**等待新样本 → `copy_to_user` 一行文本 | 用 waitqueue；非阻塞时返回 `-EAGAIN` |
| `.write` | 接受命令 0x01 → 触发一次中断 | 演示"用户态→内核态"控制通路 |
| `.unlocked_ioctl` | 4 个命令：取样本/设周期/取统计/重置 | `_IOR`/`_IOW` 生成命令号，双向校验方向与大小 |
| `.llseek` | `no_llseek` | 传感器流式接口，不支持定位 |
| `.owner` | `THIS_MODULE` | **必须**，否则模块可被卸载而代码还在运行 |

**read 的阻塞逻辑**（这是"内核态→用户态数据通路"的关键）：
```c
unsigned long seq = READ_ONCE(sd->latest.seq);
ret = wait_event_interruptible_timeout(sd->wq,
              READ_ONCE(sd->latest.seq) != seq,       /* 等"新"样本 */
              msecs_to_jiffies(2000));
if (ret == 0) return -ETIMEDOUT;      /* 超时 */
if (ret < 0)  return -ERESTARTSYS;    /* 被信号打断，让上层重试系统调用 */
```
**ioctl 规范**：未实现的命令返回 `-ENOTTY`（不是 `-EINVAL`）；用户指针先 `copy_from_user` 到内核栈变量再用，
不要直接解引用（否则可能被恶意地址攻击）。

## 2. I2C 子系统：adapter / client / smbus

### 2.1 两个核心概念

| 对象 | 含义 | 本项目 |
|------|------|--------|
| `i2c_adapter` | 一条 I2C 总线（控制器） | `i2c_get_adapter(0)` — i2c-stub 创建的虚拟总线 |
| `i2c_client` | 总线上的一个从设备（地址） | `i2c_new_client_device(adapter, &info)`，addr=0x48 |

```c
sd->adapter = i2c_get_adapter(bus);
if (!sd->adapter)
    return -EPROBE_DEFER;              /* ★ 总线还没注册好时让内核稍后重试 probe */

strscpy(info.type, "sensor_demo", I2C_NAME_SIZE);
info.addr = addr;
sd->client = i2c_new_client_device(sd->adapter, &info);
```
**`-EPROBE_DEFER` 是设备树驱动的必备技能**：真实板子上 I2C 控制器可能比传感器驱动更晚注册，
直接返回 `-ENODEV` 会让驱动永久失败；返回 `-EPROBE_DEFER` 则内核会在依赖就绪后自动重试。

### 2.2 数据读写的 API 选择

| API | 用途 | 本项目 |
|-----|------|--------|
| `i2c_smbus_read_word_data(client, reg)` | 读 16 位寄存器 | ✅ 读温度寄存器 0x00 |
| `i2c_smbus_write_word_data(client, reg, val)` | 写 16 位寄存器 | 初始化 + 模拟数据变化 |
| `i2c_smbus_read_byte_data` / `write_byte_data` | 8 位寄存器 | SHT30 部分命令 |
| `i2c_transfer()` / `i2c_master_send/recv` | 裸报文（SHT30 需要） | 真机移植时使用 |
| `regmap` 框架 | 寄存器抽象（推荐大驱动） | 本项目规模不需要 |

**温度解析**（tmp105 语义：12 位，LSB = 1/16 °C）：
```c
#define RAW_TO_MILLI(raw)  ((s32)(raw) * 1000 / 16)   /* raw=400 -> 25000 m°C = 25.000C */
```

**并发保护**：I2C 传输会睡眠，多个进程同时 read + 中断线程也在读 → 必须加锁。
本驱动用 `mutex`（因为可能睡眠，不能用 `spinlock`）。

## 3. 中断：上半部 / 下半部 与线程化中断

### 3.1 为什么必须拆分

中断处理程序运行在**硬中断上下文**：不能被调度、不能睡眠、不能等锁。
而 I2C 传输要等硬件 ACK（可能睡眠）→ **必须放到下半部**。

```
sensor_irq_hard()    上半部：只 sd->irq_count++，返回 IRQ_WAKE_THREAD
       ↓ 内核唤醒
sensor_irq_thread()  下半部（内核线程 irq/21-sensor_c）：I2C 读传感器 → 更新缓存 → 唤醒 read()
```

```c
ret = request_threaded_irq(sd->virq, sensor_irq_hard, sensor_irq_thread,
                           0, DRV_NAME, sd);
```
> ftrace 抓到线程名 `irq/21-sensor_c-59` 就是内核为这个中断创建的线程（见 docs/03）。

### 3.2 实验环境怎么"假装"有中断

真机上传感器 ALERT/DRDY 引脚接到 SoC 的 GPIO 中断控制器，`request_threaded_irq` 直接用硬件 IRQ。
QEMU 里没有这个引脚，于是驱动**自带一个极简虚拟中断控制器**：

```c
static struct irq_chip sensor_virt_irq_chip = { .name = "sensor-virt-irq" };

static int sensor_irq_domain_map(struct irq_domain *d, unsigned int virq, irq_hw_number_t hw)
{
    irq_set_chip_and_handler(virq, &sensor_virt_irq_chip, handle_simple_irq);
    return 0;
}
static const struct irq_domain_ops sensor_irq_domain_ops = { .map = sensor_irq_domain_map };

/* probe 里申请一条虚拟中断线 */
sd->irq_domain = irq_domain_create_linear(NULL, 1, &sensor_irq_domain_ops, NULL);
sd->virq = irq_create_mapping(sd->irq_domain, 0);

/* 定时器里触发 */
generic_handle_domain_irq(sd->irq_domain, 0);   /* 走完整内核中断流程 */
```
这段代码在真机上可以整段删掉，**中断处理部分（上下半部、线程化）完全不用改**。

### 3.3 触发上下文必须正确（本项目真实踩坑）

在 `write()` 系统调用（进程上下文）里直接触发中断会报：
```
WARNING: CPU: 0 PID: 65 at kernel/irq/handle.c:161
irq 21 handler sensor_irq_hard enabled interrupts
```
原因：真实中断发生 CPU 会自动关中断，而进程上下文里中断是开的。
解决：
```c
local_irq_disable();
generic_handle_domain_irq(sd->irq_domain, 0);
local_irq_enable();
```
（hrtimer 回调里不需要，因为 softirq 上下文本来就关中断——这正是"上下文"概念的活教材。）

## 4. 设备树：驱动与硬件解耦

### 4.1 匹配流程

```
dts 节点 compatible = "lucien,sensor-char"
        │  内核启动 of_platform_populate() 遍历设备树，为有 compatible 的节点创建 platform_device
        ▼
platform_device  ──匹配──>  platform_driver.of_match_table[] 中的 "lucien,sensor-char"
        │                                     │
        │                                     └─ 匹配成功 → 调用 .probe()
        ▼
probe() 里从节点读参数：i2c-bus / sensor-addr / poll-interval-ms
```
```c
static const struct of_device_id sensor_of_match[] = {
    { .compatible = "lucien,sensor-char" },   /* ★ 必须与 dts 完全一致 */
    { }
};
MODULE_DEVICE_TABLE(of, sensor_of_match);     /* ★ 少了这行，模块热插拔时无法自动匹配 */
```

### 4.2 解耦的价值（面试常问）

| 做法 | 换硬件时 | 换总线号/地址时 |
|------|---------|----------------|
| 硬编码在驱动里 | 改代码 + 重编内核 | 改代码 + 重编 |
| **设备树描述** | 只改 dts，驱动不动 | 只改 dts |

本项目实测：把 `dts/sensor-node.dts.inc` 里的 `poll-interval-ms` 从 500 改成 1000，重编 dtb 重启，
dmesg 立刻显示 `interval=1000ms`，**驱动一行代码都没改**。

### 4.3 真机的"标准写法"

真机上传感器节点通常是 I2C 控制器的**子节点**：
```dts
&i2c1 {
    sensor@44 {
        compatible = "lucien,sensor-char";
        reg = <0x44>;              /* I2C 从地址由 reg 表达 */
    };
};
```
此时驱动应注册成 **i2c_driver**（而不是 platform_driver），
或者用 `of_find_i2c_adapter_by_node(np->parent)` 从父节点拿 adapter。
本项目因为用的是 i2c-stub 动态总线（设备树里没有对应控制器），所以用 platform_driver + `i2c-bus` 属性。
两种写法见 `dts/sensor-char.dtsi` 的注释。

## 5. 并发、同步与资源管理

| 机制 | 本项目用途 | 关键点 |
|------|-----------|--------|
| `mutex` | 保护 `latest`/`stats` 与 I2C 访问 | 可睡眠的锁；中断下半部（线程）里可用 |
| `wait_queue_head_t` | read() 阻塞等待新样本 | `wake_up_interruptible` 放在锁外，避免唤醒后抢不到锁 |
| `hrtimer` | 周期性采样（模拟 DRDY） | 回调在 softirq 上下文，不能睡眠 |
| `devm_kzalloc` | 自动释放内存 | 驱动卸载/错误路径不用手动 kfree |
| `goto` 错误链 | probe 里逐级回滚 | 顺序与申请顺序相反（见 `err_*` 标签） |
| `READ_ONCE/WRITE_ONCE` | 无锁读 `seq` | 避免编译器把循环里的判断优化掉 |

**卸载顺序**（`sensor_remove`）：先停数据源，再拆中断，最后拆设备节点——
顺序反了会出现"中断处理程序访问已释放的 client"的 UAF 崩溃。
```c
hrtimer_cancel(&sd->timer);   /* 1. 停掉触发源 */
free_irq(sd->virq, sd);       /* 2. 确保没有中断在跑 */
irq_domain_remove(...);       /* 3. 拆虚拟中断域 */
device_destroy/cdev_del/unregister_chrdev_region;  /* 4. 拆字符设备 */
i2c_unregister_device/i2c_put_adapter;             /* 5. 断开 I2C */
```

## 6. 一张表自测（够用了就是"熟练"）

1. `insmod` 后 `/dev/sensor0` 是谁创建的？如果没有它会怎样？（答：devtmpfs 根据 device_create；没有则要 mknod/udev）
2. `read()` 为什么能阻塞？谁负责唤醒？（waitqueue；线程化中断处理里 wake_up）
3. I2C 读为什么不能放在 `sensor_irq_hard` 里？（会睡眠 → 硬中断上下文不允许）
4. 删掉 `MODULE_DEVICE_TABLE` 会怎样？（模块方式加载时 of 匹配表不导出，DT 匹配失效）
5. probe 返回 `-EPROBE_DEFER` 和 `-ENODEV` 的区别？（前者稍后重试，后者永久失败）
6. 换一个 I2C 地址要改哪些文件？（只改 dts）
7. `rmmod` 报 "Module is in use" 说明什么？（还有进程打开着 /dev/sensor0，或引用计数没释放）
