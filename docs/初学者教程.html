这个项目在 QEMU 里跑一个自己编译的 ARM64 Linux 内核， 然后写驱动去读一颗「虚拟的 I2C 温湿度传感器」。 它教你两件事：怎么写内核驱动，以及怎么证明自己写对了。

传感器寄存器 --I2C--> 线程化中断处理（唯一生产者）
                          ├── kfifo 环形缓冲 --waitqueue--> read/poll/epoll/SIGIO

「唯一生产者、两个出口」

只有线程化中断处理这一个地方在生产数据，所以不需要复杂的锁： 生产者侧只需要和「多个读者」协调，而读者之间用 kfifo 的索引语义 + 一把 spinlock 就够了。 这是设计驱动时的通用技巧：先把生产者收敛成一个，复杂度立刻降一档。

第 2 章　预备知识（最小必要集）

这五个概念是读这个项目代码的入场券。每节都不长，但请认真读完 —— 后面所有代码都建立在这上面。

2.1　字符设备与 file_operations

Linux 把设备分三类：字符设备（按字节流读写，如串口、传感器）、 块设备（按块读写，带缓冲，如硬盘）、网络设备（走 socket）。 传感器属于字符设备。

一个字符设备的本质就是把一堆函数指针交给内核：

static const struct file_operations sensor_fops = {
    .owner          = THIS_MODULE,
    .open           = sensor_open,      /* open("/dev/sensor0", ...) */
    .release        = sensor_release,   /* close() */
    .read           = sensor_read,      /* read() */
    .write          = sensor_write,     /* write() */
    .poll           = sensor_poll,      /* select()/poll()/epoll_wait() */
    .fasync         = sensor_fasync,    /* fcntl(F_SETFL, O_ASYNC) → SIGIO */
    .unlocked_ioctl = sensor_ioctl,     /* ioctl() —— 不走大内核锁 */
    .mmap           = sensor_mmap,      /* mmap() */
};

用户在 /dev/sensor0 上调用 read()，VFS 查 fd → 找到 cdev → 找到这个结构体 → 调 sensor_read。 理解「VFS 是分发器、驱动是回调」这个模型，就理解了一半。

注册步骤API作用
① 拿设备号alloc_chrdev_region()让内核动态分一个主设备号
② 关联 fopscdev_init() + cdev_add()把设备号与 file_operations 绑起来
③ 建类与节点class_create() + device_create()触发 udev 自动创建 /dev/sensor0，不需要手写 mknod

2.2　设备树三要素

设备树（Device Tree, DT）的作用是把「硬件是什么样」和「驱动怎么工作」分开。 同一份驱动代码，换一块板子只改设备树，不用重编译。

/* dts/sensor-node.dts.inc —— 本项目的设备树片段 */
virt_i2c: virt-i2c {
    compatible = "lucien,virt-i2c";     // ← 匹配 virt_i2c 驱动的 of_match_table
    #address-cells = <0x01>;
    #size-cells    = <0x00>;
    status = "okay";

    sensor0: sensor@48 {
        compatible = "lucien,sensor-char";   // ← 匹配 sensor_char 驱动
        reg = <0x48>;                      // ← I2C 从机地址（7 位）
        poll-interval-ms = <0x1f4>;        // ← 500ms，自定义属性
    };
};
要素含义驱动侧怎么用
compatible 「我是什么」，格式 厂商,型号 of_match_table 里列出 → 匹配上就调用驱动的 probe()
reg 「我在哪」（地址 / 寄存器范围） I2C 子节点的 reg 就是从机地址，i2c 核心自动解析后填进 client->addr
自定义属性 如 poll-interval-ms of_property_read_u32(np, "poll-interval-ms", &v) 读取
本项目的「设备树解耦」检验标准

打开 driver/sensor_char.c，搜不到任何硬件地址字面量（没有 0x48、没有总线号）。 所有硬件参数都从设备树来。这是判断一个驱动「是否可移植」的最快方法。

2.3　I2C 总线模型

I2C 是两根线的总线（SCL 时钟 + SDA 数据），一个控制器（master / adapter）下面挂多个从设备（slave / client）， 每个从设备有一个 7 位地址（本项目是 0x48）。

   一颗 I2C 控制器（adapter）
      ├── 从设备 0x48  ← sensor_char.ko 绑定（字符设备接口）
      ├── 从设备 0x49  ← sensor_iio.ko  绑定（IIO 接口）
      └── ...（本项目的 virt_i2c 为 0x48~0x4b 各维护一份独立的寄存器 bank）
内核对象代表什么本项目中
i2c_adapter一颗 I2C 控制器virt_i2c.ko 注册（带 of_node）
i2c_client总线上的一个从设备i2c 核心从设备树子节点自动枚举创建
i2c_driver「我能驱动哪些从设备」sensor_char.ko 注册后与 client 匹配 → probe(client)
regmap寄存器访问的抽象层devm_regmap_init_i2c()，之后用 regmap_read/write，不用直接碰 I2C API
为什么用 regmap 而不是直接调 i2c_transfer？

因为 regmap 把「寄存器宽度、字节序、是否需要读-改-写、要不要加锁」这些琐事统一收口， 而且同一份代码既能用在 I2C 上，也能用在 SPI／MMIO 上。真实项目里几乎没有人直接裸调 I2C API。

2.4　中断的上半部与下半部

中断处理程序（ISR）运行在硬中断上下文，这个上下文有两条铁律：

  1. 不能睡眠（不能调用任何可能阻塞的函数，包括大部分 I2C 传输）；
  2. 越快越好（它运行期间当前 CPU 不能做别的事）。

所以要读 I2C 传感器（会睡眠）就必须「分两半」：

部分上下文能做什么本项目
上半部
（hard IRQ）		 硬中断，不能睡眠 读硬件状态、记录时间戳、清中断标志 sensor_irq_hard()：只记录，返回 IRQ_WAKE_THREAD
下半部
（threaded IRQ）		 内核线程，可以睡眠 走 I2C 读数据、写缓冲、唤醒读者 sensor_irq_thread()：唯一的生产者 
/* 上半部：能少做就少做 */
static irqreturn_t sensor_irq_hard(int irq, void *data)
{
    struct sensor_dev *sd = data;
    sd->irq_ts = ktime_get();          /* 只记时间戳 */
    return IRQ_WAKE_THREAD;            /* ← 关键：请内核唤醒下半部线程 */
}

/* 下半部：可以睡眠，所以能走 I2C */
static irqreturn_t sensor_irq_thread(int irq, void *data)
{
    /* regmap_read() 会睡眠 —— 这里安全 */
    regmap_read(sd->regmap, REG_TEMP, &raw);
    /* ... 换算、写 kfifo、wake_up、kill_fasync ... */
    return IRQ_HANDLED;
}

/* 注册时同时给上下半部 */
request_threaded_irq(client->irq, sensor_irq_hard, sensor_irq_thread,
                     IRQF_ONESHOT, "sensor", sd);

2.5　内核编程的三条铁律

铁律一：先问「我能睡吗」

硬中断、软中断、自旋锁临界区、原子上下文 —— 都不能睡眠。 睡眠 = 调用 mutex_lock、kmalloc(GFP_KERNEL)、I2C/SPI 传输、copy_to_user 等。 项目里 sd->lock 是 mutex，所以中断上下文一律不许碰它。

铁律二：用户态内存不能直接解引用

ubuf 来自用户态，可能是个非法地址、也可能在访问时被换出。 必须通过 copy_to_user() / copy_from_user()，并且检查返回值。 本项目在 copy_to_user 失败时会把样本放回队列，而不是默默丢掉 —— 因为 ring_count + kfifo_dropped == irq_count 这个守恒式会立刻暴露「样本蒸发」。

铁律三：谁分配谁释放，顺序不能错

本项目 release() 里必须先摘除异步通知，再清私有数据：

sensor_fasync(-1, file, 0);   /* 必须在下一行之前 */
file->private_data = NULL;

因为 sensor_fasync() 内部要读 file->private_data 拿 sd。 顺序反了就是 use-after-free。

5.1　阶段 01　四种 IO 模型

要解决什么问题

起点是一个「只有阻塞 read」的字符设备。这意味着用户态没法把它接进事件循环 （不能 epoll、不能异步通知），在实际应用里几乎不可用。

核心认知：这四种模型不是四个功能，而是同一个事实的四种通知方式 —— 「现在有数据可读」这个事实，可以「让进程睡等」、「让进程稍后再来」、「让 epoll 告诉我」、「给我发信号」。

模型谁在等内核怎么让对方知道
阻塞 read进程睡在内核里wake_up() 唤醒等待队列
非阻塞 read没人等返回 -EAGAIN，用户态自己重试
poll / epoll用户态睡在 epoll_wait等待队列 + epoll 就绪队列
fasync / SIGIO用户态在干别的内核主动发信号

关键 API 与约束

/* 阻塞：睡在等待队列上，最多等 SENSOR_READ_TIMEOUT_MS */
ret = wait_event_interruptible_timeout(
        sd->wq, sensor_has_new_sample(sd),
        msecs_to_jiffies(SENSOR_READ_TIMEOUT_MS));
/* 返回值语义一定要记准：
   0  = 超时     <0 = 被信号打断（-ERESTARTSYS）   >0 = 条件满足（剩余 jiffies） */

/* 非阻塞：驱动自己负责检查 O_NONBLOCK，VFS 不管 */
if (file->f_flags & O_NONBLOCK)
    return -EAGAIN;      /* 必须返回 EAGAIN，不能返回 0 —— epoll 边沿触发依赖它 */

/* poll：只做两件事，顺序不能反 */
static __poll_t sensor_poll(struct file *file, poll_table *wait)
{
    struct sensor_dev *sd = file->private_data;

    poll_wait(file, &sd->wq, wait);       /* ① 先登记（只登记，不睡眠！） */
    if (sensor_has_new_sample(sd))
        return EPOLLIN | EPOLLRDNORM;     /* ② 再回答当前状态 */
    return 0;
}

/* fasync + 发送侧 */
static int sensor_fasync(int fd, struct file *file, int on)
{
    struct sensor_dev *sd = file->private_data;
    return fasync_helper(fd, file, on, &sd->fasync);   /* 链表维护交给辅助函数 */
}

/* 下半部里，紧跟 wake_up 之后：*/
wake_up_interruptible(&sd->wq);
kill_fasync(&sd->fasync, SIGIO, POLL_IN);
这一步最容易踩的三个坑
  1. 顺序坑：先判断状态、再 poll_wait → 两步之间到达的新样本会丢唤醒（偶发卡死）。
  2. 上下文坑：在 .poll 里睡眠或持锁。.poll 会被 epoll_wait 反复调用，只该做「登记 + 报状态」。
  3. 释放顺序坑：release() 里先清 private_data 再摘 fasync → use-after-free。

怎么验证

用户态程序 user/io_models_test.c 把每项结果打印成 [IO] 键=值， 测试脚本 tests/phases/01-io-models.sh 读取这些键并判定：

为什么 SIGIO 计数通常是 1？

标准信号不排队：多个 SIGIO 会合并成一次 pending，所以收到 1 次是完全正常的。 判定用 ≥ 1 而不是精确计数。想精确计数需要改用实时信号（SIGRTMIN+n）+ F_SETSIG。

5.2　阶段 02　设备树解耦 + i2c_driver + regmap

要解决什么问题

阶段 01 的驱动里，硬件参数是写死在代码里的（I2C 总线号、从机地址）。 换一块板子就要改代码重新编译 —— 这就是「不可移植」。这个阶段把它变成 标准的 i2c_driver 模型：参数全从设备树来，寄存器访问全走 regmap。

三步改造

  1. 自己造一个 I2C 控制器（virt_i2c.c）：写一个 platform_driver， 注册带 of_node 的 i2c_adapter，并用 i2c_add_adapter 之外的路径 提供「寄存器级」的读写模拟。
    为什么不用内核自带的 i2c-stub？ 因为 stub 的 adapter 没有设备树节点， i2c 核心无法从它下面枚举出子设备。
  2. 改成标准 i2c_driver：不再手工 i2c_new_client_device()， 而是注册 i2c_driver + of_match_table，让 i2c 核心去枚举设备树子节点并回调 probe()。
  3. 用 regmap 替掉裸 I2C：devm_regmap_init_i2c() 之后， 读写变成 regmap_read(sd->regmap, REG_TEMP, &raw)。
/* 设备树：控制器 → 子设备两级结构 */

};

怎么判断你做到「解耦」了

在 sensor_char.c 里搜 0x48、搜总线号 —— 应该一个都搜不到。 硬件地址只出现在设备树里。client->addr 由 i2c 核心自动填好， 驱动只管用。这是可移植性的可检验标准。

19 项检查，重点看这几类：设备树是否解析到 compatible、i2c client 是否被创建、 从机地址是否等于 0x48、regmap 读写是否与模拟寄存器一致、模块加载顺序是否正确。

5.3　阶段 03　kfifo 环形缓冲 + mmap 零拷贝

要解决什么问题

阶段 02 之前，驱动只保留最新一个样本（latest）。问题是：

采样节奏由硬件决定：每 500ms 一个样本
读取节奏由应用决定：可能 3 秒读一次，也可能一直不读

→ 只保留最新值时，中间的样本就静默丢失了

这个阶段的数据通路是「一个生产者、两个出口」：

传感器寄存器 --I2C--> 线程化中断处理（唯一生产者）
                          ├── kfifo 环形缓冲（64 个样本）--waitqueue--> read/poll/epoll/SIGIO
                          └── mmap 共享页（seqlock 保护）-----------> 用户态直接读（零拷贝）
     另外保留 latest 供 ioctl(GET_SAMPLE) 立即取值

两个关键技术点

① kfifo 环形缓冲与溢出策略

/* 生产（线程化中断里） */
if (kfifo_in_spinlocked(&sd->ring, &s, sizeof(s), &sd->ring_lock) != sizeof(s)) {
    sd->stats.kfifo_dropped++;      /* ← 队列满：丢「新」样本，但计数 */
}

/* 消费（read 里） */
if (kfifo_out_spinlocked(&sd->ring, &snap, sizeof(snap), &sd->ring_lock) == sizeof(snap))
    break;                        /* 取到了 */
为什么是「丢新不丢旧」？
  1. 已排队的数据是「用户态还欠着没读的历史」，静默改写历史比丢新更难排查；
  2. kfifo_dropped 让「丢了多少」变成可观测量，而不是无声无息；
  3. 传感器数据通常是时序敏感的，保留更早的时间序列更有价值。

代价是最新样本可能进不了队列 —— 但它仍然在 latest / 共享页里，所以「读最新值」这条路径不受影响。

② mmap 零拷贝与 seqlock

/* read()   ：内核缓冲 --copy_to_user--> 用户缓冲   每次读都要拷贝 + 一次系统调用
/* mmap()   ：用户页表直接指向内核分配的物理页      不拷贝，之后取值完全在用户态 */

/* 用户态：映射一页，直接读结构体 */
struct sensor_shm *shm = mmap(NULL, 4096, PROT_READ, MAP_SHARED, fd, 0);
do {
    seq = shm->seq_begin;          /* 读前序号 */
    smp_rmb();
    temp = shm->temperature_mc;    /* 读数据 */
    smp_rmb();
} while (shm->seq_end != seq);      /* 序号变了 → 读到撕裂数据，重读 */
关键设计决策：为什么共享页不加锁而要自己实现 seqlock 语义？

因为 用户态不可能持有内核锁。你没法让用户进程在读取共享页时去拿内核的 mutex。 所以只能用「序号 + 内存屏障 + 重试」这种无锁但可检测撕裂的方案：

写者：seq 变奇数 → smp_wmb() → 写数据 → smp_wmb() → seq 变偶数
读者：读 seq（奇数说明正在写）→ 读数据 → 再读 seq，不一致就重读

这个决策是必须真正理解内核才能做对的，而且它在这个项目里用 KCSAN（内核并发检测器）验证过无数据竞争。

怎么验证

40 项检查，是六个阶段里最多的。重点覆盖：多进程并发读写不丢数据、校验 ring_count + kfifo_dropped == irq_count 这个守恒式、 mmap 映射的权限与长度校验（必须只读、不能超过一页）、seqlock 重试逻辑是否真的能检测撕裂。

5.4　阶段 04　sysfs 与 debugfs

要解决什么问题

驱动装上了，但你（和运维）怎么看见它在干什么？怎么在不改代码、不重编译的情况下调参数？ 这是生产驱动和玩具代码的分界线。

子系统定位本项目暴露的内容
sysfs 稳定 ABI，给用户态脚本和系统管理用 interval_ms（采样周期，可读写）、seq、i2c_errors、ring_capacity
debugfs 调试用，无 ABI 保证，可以随时变 stats（运行统计）、ring（环形缓冲内容）、regs（寄存器现场） 
/* sysfs：一行代码定义属性，读写回调各自实现 */
static ssize_t interval_ms_show(struct device *dev, struct device_attribute *attr, char *buf)
{
    struct sensor_dev *sd = dev_get_drvdata(dev);
    return sysfs_emit(buf, "%u\n", READ_ONCE(sd->interval_ms));
}

static ssize_t interval_ms_store(struct device *dev, struct device_attribute *attr,
                                 const char *buf, size_t count)
{
    struct sensor_dev *sd = dev_get_drvdata(dev);
    unsigned long v;
    if (kstrtoul(buf, 0, &v)) return -EINVAL;
    /* 范围校验 + 生效动作（重设 hrtimer 周期） */
    sensor_apply_interval(sd, v);
    return count;
}
static DEVICE_ATTR_RW(interval_ms);   /* 宏生成 show/store 配对 */
sysfs 与 debugfs 的分工，一句话记住

sysfs 是接口（会被人依赖，改动要谨慎）；debugfs 是窗口（只给自己看，随便改）。 所以「采样周期」这种用户真正需要的参数放 sysfs，「内部计数器」这种调试信息放 debugfs。

写 *_store 回调的三个隐性要求
  1. 返回值必须是 count（而不是 0），否则用户态的 echo 会报错；
  2. 必须做范围校验：用户态可能写入 0、负数或超大值；
  3. 写入通常要触发生效动作（本项目要重设 hrtimer 周期），并考虑与并发读取的同步。

怎么验证

53 项 —— 数量最多，因为大多是「字段级」的断言：ls 属性是否存在、 默认值是否正确、写入非法值是否被拒绝（权限与只读性）、stats 里的计数是否自洽等。 权限位与只读性是重点：把只读属性写坏、或让普通用户能改关键参数，都是真实驱动里的常见漏洞。

5.5　阶段 05　IIO 子系统驱动

要解决什么问题

前面四个阶段，你是自己造轮子：自定义 fops、自定义 ioctl、自定义 sysfs。 这在玩具项目里可行，但真实内核有标准子系统 —— 传感器类设备的标准答案是 IIO （Industrial I/O）。用 IIO 的好处是：内核里的通用工具（iio_generic_buffer、 libiio）和硬件描述（iio_chan_spec）能直接复用。

本项目两个驱动并存，这本身就是最好的对比教材：

字符设备版 sensor_char.koIIO 版 sensor_iio.ko
绑定的从机0x480x49（同一控制器，独立 bank）
用户态接口/dev/sensor0 + 自定义 ioctl/dev/iio:device0 + 标准 iio_chan_spec
数据获取自己写 read/poll/mmaptriggered buffer + 触发器，由 IIO 核心管理
触发源自己注册 request_threaded_irqhrtimer trigger（IIO 的触发器框架）
通用工具支持无有（iio_generic_buffer 等）
代码量1676 行368 行
368 行 vs 1676 行，这就是「子系统」的价值

同样一个传感器，接入 IIO 只需要 368 行（而这个数字恰好落在真实内核 IIO 驱动的中位数 342 行附近）。因为「环形缓冲、字符设备注册、poll 语义、缓冲区管理」这些 IIO 核心已经做完了 —— 你只写「这颗芯片的寄存器怎么读写、有哪些通道」。

/* 描述「我有哪些数据通道」—— 这是 IIO 驱动的核心数据结构 */
static const struct iio_chan_spec sensor_iio_channels[] = {
    {
        .type = IIO_TEMP,
        .info_mask_separate = BIT(IIO_CHAN_INFO_RAW) |
                              BIT(IIO_CHAN_INFO_SCALE),
        .scan_index = 0,
        .scan_type = { .sign = 's', .realbits = 16, .storagebits = 16 },
    },
    {
        .type = IIO_HUMIDITYRELATIVE,
        .info_mask_separate = BIT(IIO_CHAN_INFO_RAW) |
                              BIT(IIO_CHAN_INFO_SCALE),
        .scan_index = 1,
        .scan_type = { .sign = 'u', .realbits = 16, .storagebits = 16 },
    },
};

static int sensor_iio_read_raw(struct iio_dev *indio_dev,
                              struct iio_chan_spec const *chan,
                              int *val, int *val2, long mask)
{
    switch (mask) {
    case IIO_CHAN_INFO_RAW:      /* 读原始值 */
        return IIO_VAL_INT;
    case IIO_CHAN_INFO_SCALE:    /* 换算比例：用户态拿 raw*scale 得到物理量 */
        *val = 1; *val2 = 1000;
        return IIO_VAL_INT_PLUS_MICRO;
    }
    return -EINVAL;
}

怎么验证

22 项：/dev/iio:device0 是否出现、iio_chan_spec 是否被正确导出 （/sys/bus/iio/devices/iio:device0/ 下的 in_temp_raw 等）、 triggered buffer 是否能被 trigger 推着跑、以及两个驱动同时加载互不干扰。

5.6　阶段 06　Runtime PM 与 KUnit

要解决什么问题

两件看似无关、但都是「从能跑变成专业」的事：

  1. 省电：设备空闲时应该能自动挂起（Runtime PM），否则手机/嵌入式设备的电池撑不住；
  2. 可测：把纯逻辑抽出来做单元测试（KUnit），而不是每次都启动 QEMU 做集成测试。

① Runtime PM：引用计数模型

/* open：占一个引用 —— 只要有人打开着，就不允许自动挂起 */
static int sensor_open(struct inode *inode, struct file *file)
{
    struct sensor_dev *sd = ...;
    int ret = pm_runtime_resume_and_get(&sd->client->dev);
    /*      ↑ 用 _and_get 而不是 pm_runtime_get_sync：
           后者在出错时会留下一个引用，导致设备再也挂不下去（经典泄漏） */
    if (ret < 0) return ret;
    ...
}

/* close：归还引用，并按 autosuspend 延迟安排挂起 */
static int sensor_release(struct inode *inode, struct file *file)
{
    pm_runtime_mark_last_busy(dev);      /* 记录「最后一次使用时刻」 */
    pm_runtime_put_autosuspend(dev);     /* 引用归零后，延迟 1 秒再挂起 */
}

/* 挂起/恢复回调：真正断电断时钟的地方 */
static int sensor_runtime_suspend(struct device *dev) { ... }
static int sensor_runtime_resume(struct device *dev)  { ... }
为什么 open 时要「抓住」一个 PM 引用？

否则会出现这种情况：进程正在 read() 阻塞等数据，此时设备因为「空闲」被自动挂起， 采样停了，进程就一直等到超时 —— 用户看到的现象是「驱动坏了」。 引用计数就是用来表达「有人在用，别关」的。

② KUnit：把纯逻辑抽出来测

关键设计：把温湿度换算公式抽到一个纯头文件 sensor_calc.h（99 行，无内核依赖）， 这样 KUnit 模块可以直接测它，不需要真实硬件、不需要 QEMU 全流程。

static void sensor_calc_temp_test(struct kunit *test)
{
    /* 表驱动：输入原始寄存器值 → 期望的物理量（毫摄氏度） */
    KUNIT_EXPECT_EQ(test, sensor_raw_to_milli_celsius(0x0000), -40000);
    KUNIT_EXPECT_EQ(test, sensor_raw_to_milli_celsius(0x7FFF), 125000);
    /* 边界值：负温度、量程两端 */
}

static struct kunit_suite sensor_calc_suite = {
    .name  = "sensor_calc",
    .test_cases = sensor_calc_test_cases,
};
kunit_test_suite(sensor_calc_suite);
为什么 KUnit 能编成外部模块？

因为 kunit_* 系列符号在内核里是 EXPORT_SYMBOL_GPL， 而本模块是 GPL 许可 —— 所以可以直接 insmod 一个 KUnit 测试模块， 不需要把测试编进内核。这也是为什么项目必须用 GPL 兼容许可（见 LICENSE）。

怎么验证

32 项：Runtime PM 的引用计数是否正确增减、open 期间是否真的不会挂起、 close 后 1 秒是否真的挂起、恢复后采样是否继续；KUnit 套件的 5 个用例 是否 pass:5 fail:0（判定同时看用例名与计数）。

第 6 章　测试方法论：本书最值钱的一章

前面五章讲「怎么写驱动」，这一章讲「怎么证明你写对了」。 绝大多数人跳过这一章，然后在面试时被一句「你怎么知道你的测试有效？」问住。

6.1　检查项要能当结论读

✗ 差的检查项 
[CHECK:PASS] 检查1
[CHECK:PASS] poll 测试
[CHECK:PASS] 功能正常
✓ 好的检查项 
[CHECK:PASS] 非阻塞 read 返回 EAGAIN（实测 1 次）
[CHECK:PASS] poll 为电平触发、无忙轮询（3 秒内仅唤醒 7 次）
[CHECK:PASS] ftrace 捕获到 kill_fasync 调用（实测 8 次）

两个要求：

  1. 名字本身要能当结论读（而不是「检查1」「功能正常」）；
  2. 把实测值写进名字里 —— 这样半年后从日志复查时，你能看出「7 次」是不是异常。

6.2　什么叫「假绿」

定义

假绿：测试全 PASS，但被测的东西其实是错的。 这比「测试失败」危险得多 —— 失败会逼你去修，假绿会让你带着 bug 继续往上盖楼。

本项目真实发生过一次，而且抓它的方法很值得学：

项目内容
怎么发现的独立验证者做了一个破坏性变体：把 sensor_poll() 里的 poll_wait() 注释掉，重新编译，跑同一套测试
结果9 项依然全 PASS —— 说明这套测试根本测不出「有没有注册等待队列」
为什么当时的判定是「epoll_wait 至少返回过一次可读」。而 epoll_ctl(ADD) 时内核会立刻调一次 ->poll，此时队列里恰好有数据，fd 就直接进了就绪队列。第一次 epoll_wait 立即返回 —— 完全不需要 poll_wait
真正的危害不是「驱动写错了」，而是回归保护是假的：后续阶段都会改 read/poll 的数据源，任何一次重构删掉 poll_wait 都会静默全绿

6.3　负控实验：证明你的测试会失败

负控实验（Negative Control）：主动往代码里注入一个已知缺陷，然后验证 「测试套件必须失败」。如果它仍然全绿，说明测试无效。

# 注入缺陷（只注释掉一行 —— 这是最小可检测的破坏）
sed -i'' -e 's|^\tpoll_wait(file, &sd->wq, wait);|/* 负控实验（临时） */|' driver/sensor_char.c

# 重新构建 + 跑同一套测试
limactl shell dev bash -c 'TEST=01-io-models bash scripts/13-vm-fast-cycle.sh'
bash scripts/21-macos-sync-artifacts.sh
bash scripts/22-macos-run-test.sh 01-io-models 180        # → 11 PASS / 5 FAIL ✓ 抓住了

# 恢复并复验
git checkout -- driver/sensor_char.c
limactl shell dev bash -c 'TEST=01-io-models bash scripts/13-vm-fast-cycle.sh'
bash scripts/21-macos-sync-artifacts.sh && bash scripts/22-macos-run-test.sh 01-io-models 180   # → 16 PASS

A 健康驱动正常16 PASS / 0 FAIL
B 负控漏写 poll_wait()11 PASS / 5 FAIL ← 成功抓住
C 恢复后正常16 PASS / 0 FAIL
负控实验必须遵守的纪律：绝不在交付目录里做

项目里真实发生过两次事故：

  • 阶段 05：实现者做完负控（把触发器里的温/湿度通道互换，留了 NEGCTRL-B 标记）忘记还原就汇报「全绿」。 结果交付源码开箱即 19 PASS / 3 FAIL —— 被别人重建后当场复现。
  • 阶段 06：验证者做负控时，编辑器报错但文件其实已被写入， 残留了 /* NC-... */ 改动。

正确做法三选一：① 复制 driver/ 到独立目录改副本； ② git worktree add 另开一棵树；③ 实验后 git checkout -- <file> 并逐文件比对 sha256。

「git 是干净的」不能证明交付文件没被污染

因为新增的交付文件常常是 untracked，git status 只显示「有新文件」， 看不到内容被改过。所以项目里有一个专门的交付门禁：

bash scripts/23-check-worktree-clean.sh

它扫描代码里的 NC- / NEGCTRL / EXPERIMENT 标记、 被注释掉的关键语句、以及未跟踪文件的 sha256。

6.4　三条可复用的原则

原则一：上界检查抓不到「太少」

当时套件里有 epoll_wakeups ≤ 12（用来抓忙轮询）。坏驱动的实测值是 0 次， 而 0 ≤ 12 照样 PASS。上界与下界必须成对出现。

检查抓什么坏驱动实测
epoll_wakeups ≤ 12（上界）忙轮询（消费后仍报可读）0 —— PASS（漏了）
epoll_wakeups ≥ 3（下界）根本没注册等待队列0 —— FAIL（抓到）
epoll_first_wakeup_ms ≤ 1000（延迟）同上，且分辨力最强2503ms —— FAIL（抓到）

原则二：状态类断言要双向

「电平触发」有两半，必须都测：

  • 下界：消费掉数据后，poll 立刻不再可读（poll_after_consume == 0）；
  • 上界：没消费时，poll 持续可读（poll_unread_hits == 5，连续 5 次都要为真）。

只测前半边的话，「one-shot 式」的错误实现也能通过。

原则三：取不到值，就用必然失败的默认值

/* 用户态程序没有输出这个键时，不要当作「跳过」，而要当作「失败」 */
epoll_first_wakeup_ms=$(val_or "$OUT" epoll_first_wakeup_ms 99999)
poll_after_consume=$(val_or   "$OUT" poll_after_consume   1)     /* 1 = 失败 */
poll_unread_hits=$(val_or     "$OUT" poll_unread_hits     0)     /* 0 = 失败 */

否则会出现这种情况：只要删掉用户态程序的打印语句，测试就全绿了。

同理，「能力检测」不能静默跳过：原本 ftrace 用不了时该项直接跳过， 导致检查数从 9 悄悄变成 8 却仍显示全绿。修复方式是把它变成一个显式检查项 （FT_OK == 1），能力缺失要体现在结论里，而不是消失。

6.5　完整案例：漏写一行 poll_wait 如何被抓

失败检查项实测值（原始日志）
首次唤醒延迟 ≤ 1000ms[IO] epoll_first_wakeup_ms=2503　← 睡满超时
poll 唤醒次数下界 ≥ 3[IO] epoll_wakeups=0　← 一次都没被唤醒
epoll 在 3 秒窗口内报告可读[IO] epoll_wait_ok=0
io_models_test 退出码为 0实际 1
程序整体结论为 PASS[IO] OVERALL=FAIL

两条新增检查独立抓住同一缺陷（延迟 2503ms + 唤醒数 0），而且都是 原始实测数值，不是程序自述的字符串。对照之下，「唤醒次数上界 ≤ 12」 在坏驱动上仍是 PASS（0 ≤ 12）—— 这正好解释了为什么上一版抓不到。

这就是「可证伪」的含义

一个测试只有在「被测对象错了它会失败」时才有意义。 想验证这一点，唯一的方法就是真的把它弄错一次，看它会不会失败。 这也是这个项目在简历上最有说服力的一句话： 用负控实验证明了测试套件真的能失败，并据此发现并修复了 3 处「假绿」缺口。

# 1) 选择「按函数过滤」模式

echo function > $TR/current_tracer

# 2) 只关心这一个函数
echo kill_fasync > $TR/set_ftrace_filter

# 3) 开始录制
echo 1 > $TR/tracing_on
# ... 让被测代码跑起来 ...

# 4) ★ 关键顺序：先停 tracing，读走结果，最后才切回 nop
echo 0 > $TR/tracing_on
grep -c kill_fasync $TR/trace          # ← 必须在下一行之前读！
echo nop > $TR/current_tracer          # 切回 nop 会清空 trace 缓冲区
这个坑真实踩过：ftrace 证据永远是 0

当时脚本在把 current_tracer 切回 nop 之后才去读 trace 文件 —— 而切换 tracer 会清空 trace 环形缓冲区，所以永远读到 0。 排查过程也很典型：SIGIO 明明收到了（sigio_count=1），说明 kill_fasync 必然被调用过， 所以问题一定出在采集方式而不是代码。修复后捕获到 8 次调用。

第 9 章　从实验到真机，以及面试怎么讲

9.1　移植到真机只需改三处

这个项目虽然是虚拟环境，但驱动代码本身是真机上能用的。以「树莓派 + SHT30 传感器」为例：

#改什么怎么改
1 设备树 不再用虚拟控制器，把节点挂到真实的 &i2c1 下面， 从机地址改成 0x44（SHT30）
2 拿 adapter 的方式 用 of_find_i2c_adapter_by_node() 从父节点取，而不是读 i2c-bus 编号
3 读数据的命令字与换算公式 sensor_irq_thread() 里换成 SHT30 的读数命令 （i2c_smbus_write_i2c_block_data + i2c_master_recv）， 换算改成 -45 + 175 * S / 65535
为什么只要改三处？

因为「设备树解耦」做对了 —— 硬件地址不在代码里。 这正是阶段 02 的价值所在，也是移植时的直接回报。 中断那条路径（request_threaded_irq + 上下半部）在真机上一行都不用改： 实验里是 hrtimer 触发虚拟中断，真机上是传感器 ALERT 引脚接到 GIC，驱动看到的东西是一样的。

9.2　面试怎么讲这个项目

错误讲法（大多数人这样讲）

「我写了一个 Linux 字符设备驱动，实现了 read/write/ioctl，用 I2C 读温湿度传感器，还做了 IIO 和 Runtime PM。」

问题：这是清单罗列，面试官无法判断你做得多深，也无法区分你和「跟着教程敲了一遍」的人。

正确讲法（讲「为什么」和「怎么证明」）

1）先讲一个具体的技术决策

「mmap 共享页我没有加锁，而是自己实现了 seqlock 语义 —— 因为用户态不可能持有内核锁， 所以只能用『序号 + 内存屏障 + 重试』来检测撕裂。这里用了 smp_wmb 和 READ_ONCE， 并用 KCSAN 验证过无数据竞争。」

2）再讲你怎么证明它是对的

「我做了负控实验：主动往代码里注入缺陷（比如注释掉 poll_wait、互换温湿度通道）， 验证测试套件必须失败。第一次做的时候发现 —— 删掉 poll_wait 后测试依然全绿， 说明我的测试是无效的。后来我加了『首次唤醒延迟』这个观测量才抓住它： 正确实现是 502ms（约一个采样周期），坏驱动是 2503ms（睡满超时）。 我用这个方法一共发现并修复了 3 处「假绿」缺口。」

3）最后说规模与广度

「4 个内核模块，用到了 40 个内核子系统头文件 —— I2C、regmap、irq_chip/irq_domain、kfifo、mmap、 poll/epoll、fasync、sysfs、debugfs、Runtime PM、IIO、KUnit。7 套自动化测试共 197 项断言。」

三个要避开的坑
  1. 不要报代码行数。面试官 clone 下来跑 cloc 会对不上 （注释占 40%）。要用「模块数 / 子系统数 / 断言数」这类可核验的说法。
  2. 不要回避「虚拟硬件」。主动说：「我用虚拟控制器替代真实传感器， 目的是让整条链路可复现、可注入故障。移植到真机只需改三处 —— 设备树、取 adapter 的方式、换算公式。」 主动承认 + 给出补救方案，比被追问出来好得多。
  3. 准备被问「你怎么知道测试有效」。这是最能拉开差距的问题， 而你有现成的、带日志证据的答案（第 6 章）。

9.3　继续深入的学习路线

顺序做什么收获
1 亲手做破坏性实验：注释掉 poll_wait、把 -EAGAIN 改成 return 0、 把 poll_wait 移到状态判断之后 亲眼看到「假绿」被抓住、ET 模式失效、丢唤醒。比读十遍文档管用。
2 读内核源码：fs/select.c 的 do_poll()、 fs/eventpoll.c 的 ep_item_poll()、kernel/sched/wait.c 看清「驱动只登记、VFS 才睡」这条完整链路

附录 B　术语表

字符设备（char device）
按字节流读写的设备，通过 /dev/xxx 访问，对应内核里的 file_operations。
VFS（Virtual File System）
文件系统抽象层。用户态 read() 最终由它分发到驱动的回调函数。
设备树（Device Tree, DT / DTS / DTB）
描述硬件拓扑的数据结构。DTS 是源文件，编译后成 DTB，由 bootloader 传给内核。 用来把「硬件是什么样」与「驱动怎么写」分开。
compatible
设备树节点的「我是什么」，格式 厂商,型号。驱动用它匹配设备。
probe()
驱动与设备匹配成功后内核调用的初始化函数。一个驱动的入口就在这里。
i2c_driver / i2c_client / i2c_adapter
分别是「驱动的从设备匹配表」、「总线上的一个从设备」、「一颗 I2C 控制器」。
regmap
寄存器访问抽象层。统一处理寄存器宽度、字节序、读-改-写、加锁等细节， 让同一份驱动代码可以用在 I2C / SPI / MMIO 上。
上半部 / 下半部（top half / bottom half）
中断处理的分层。上半部在硬中断上下文（不能睡眠，要快）； 下半部在内核线程里（可以睡眠）。本项目用 request_threaded_irq 实现。
等待队列（wait queue）
内核里「一批正在等某个条件的进程」的链表。 wait_event_* 睡眠、wake_up_* 唤醒。是阻塞 IO 的基础。
poll_wait()
在驱动的 .poll 里登记等待队列（不睡眠）。 真正睡眠由 poll()/epoll_wait() 系统调用负责。
电平触发 / 边沿触发（level / edge triggered）
电平触发：只要「有数据」这个状态成立，每次查询都报可读（驱动负责实现）。 边沿触发：只在状态从「不可读」变「可读」时报一次（由 epoll 在用户态层实现）。
fasync / SIGIO
异步通知机制。内核通过信号告诉用户态「有数据了」， 用户态不需要阻塞也不需要轮询。fasync_helper() 登记，kill_fasync() 发送。
kfifo
内核提供的环形缓冲（FIFO）。单生产者单消费者时天然免锁；多读者需要自己加锁。
mmap 零拷贝
把内核分配的物理页直接映射进用户态页表，用户态读取时不再经过 copy_to_user。
seqlock
一种无锁读的一致性方案：写者用序号（奇=正在写）标示，读者读前后各读一次序号， 不一致就重读。适合「读多写少」且读者不能持锁的场景（如 mmap 共享页）。
sysfs / debugfs
sysfs 暴露稳定的用户接口（/sys/，改动要谨慎）； debugfs 暴露调试信息（/sys/kernel/debug/，无 ABI 保证）。
IIO（Industrial I/O）
传感器类设备的标准子系统。提供通道描述、缓冲区、触发器等通用机制， 让你只写「这颗芯片怎么读写」。
Runtime PM
运行时电源管理。设备空闲时自动挂起，使用时自动恢复。 用引用计数表达「现在有人在用，别关」。
KUnit
内核里的单元测试框架，可以编成外部模块直接 insmod 运行。
KCSAN
Kernel Concurrency Sanitizer，内核的数据竞争检测器。 需要专门编译一个带 KCSAN 的内核（本项目用 scripts/15）。
ftrace
内核函数跟踪框架。可以记录「哪个函数被调用了、调用了几次」，是内核调试的主力工具。
initramfs
启动时先加载的一个小型内存文件系统，里面放驱动模块和初始化脚本。 本项目把 .ko 和测试脚本都打包进去，这样 QEMU 启动后能立刻加载驱动跑测试。
负控实验（negative control）
故意注入一个已知缺陷，验证「测试套件必须失败」。 如果仍然全绿，说明测试无效。这是证明测试有效性的唯一方法。
假绿（false green）
测试全 PASS 但被测对象其实是错的。比测试失败更危险。
