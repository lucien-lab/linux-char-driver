# 开发与验证守则（实现者与验证者必读）

> 本文件是 **linux-char-driver 项目升级工程的操作手册**。
> 任何参与实现的成员在动手前必须通读本文；它规定了环境、开发循环、测试协议、
> 编码规范、验证门槛与禁止事项。

---

## 一、工程目标

把已有的「Linux 字符设备驱动 + I2C 传感器」个人项目，按简历条目升级为
**「从字符设备到 IIO 子系统」的全栈驱动项目**。六个阶段对应简历里的六条 bullet：

| 阶段 | 简历 bullet 对应内容 | 主要交付 |
|---|---|---|
| 01 | 四种 IO 模型（阻塞 / 非阻塞 / poll·epoll / fasync·SIGIO） | fops 补全 + 用户态四种模型验证程序 |
| 02 | 设备树解耦匹配 + 标准 i2c_driver 模型 + regmap | 虚拟 I2C 控制器 + i2c 子节点匹配 + regmap 重构 |
| 03 | kfifo 环形缓冲 + mmap 零拷贝 + 多进程并发无竞态 | 数据通路重构 + 并发压力测试 |
| 04 | sysfs 暴露设备参数、debugfs 导出运行统计 | 两套内核用户接口 |
| 05 | IIO 子系统驱动（triggered buffer + hrtimer trigger） | 新增 sensor_iio.c，与字符设备版并存对比 |
| 06 | Runtime PM + KUnit | 电源管理 + 内核单元测试 |

每个阶段结束都必须：**代码编译通过 → QEMU 里跑出可复现的检查结论 → 写出实现文档与知识点文档**。

## 二、环境架构（三层，各司其职）

```
┌─────────────────────────────────────────────────────────────────────┐
│ macOS 宿主（Apple Silicon）                                          │
│  ├── 项目目录（可写）：/Users/lucien/workspace/self-study/projects/linux-char-driver
│  ├── qemu-system-aarch64 11.1  ← 真正跑内核的地方（TCG + cortex-a72）
│  ├── dtc / python3                                               │
│  └── 测试结果解析（scripts/22-macos-run-test.sh）                  │
└───────────────▲──────────────────────────────┬──────────────────────┘
                │ limactl copy（产物拷出）        │ limactl shell（命令执行）
┌───────────────┴──────────────────────────────▼──────────────────────┐
│ Lima 虚拟机 "dev"（Ubuntu 26.04 / aarch64 / 4 vCPU）                  │
│  ├── ~/kernel-build/linux-6.6.156  ← 已编译好的内核树（gcc-13）        │
│  ├── ~/lab/driver|user|tests       ← 从宿主只读挂载拷进来的源码副本    │
│  └── ~/lab/out/                    ← 构建产物（initramfs / Image / ko）│
└─────────────────────────────────────────────────────────────────────┘
```

**关键约束**：

1. **macOS 的 `$HOME` 在虚拟机里是只读挂载**。虚拟机内只能写 `~/`（即 `/home/lucien.guest`），
   产物必须用 `limactl copy` 拷回宿主。
2. **macOS 上没有 aarch64 交叉编译器**，内核模块只能在虚拟机里编译。
3. **虚拟机里没有 Apple 虚拟化加速**，QEMU 装在 macOS 侧；且
   `-accel hvf -cpu host` 下 ftrace 会挂死（已验证），必须用 `-accel tcg -cpu cortex-a72`。

## 三、一条命令的开发循环（每个阶段重复 N 次）

```bash
cd /Users/lucien/workspace/self-study/projects/linux-char-driver

# ① 在虚拟机里编译模块 + 用户态程序 + 打包 initramfs（约 10 秒）
limactl shell dev bash -c 'TEST=<阶段名> bash /Users/lucien/workspace/self-study/projects/linux-char-driver/scripts/13-vm-fast-cycle.sh'

# ② 把产物从虚拟机拷到 artifacts/
bash scripts/21-macos-sync-artifacts.sh

# ③ 启动 QEMU 跑该阶段测试，自动给出 PASS/FAIL 结论（约 10~30 秒）
bash scripts/22-macos-run-test.sh <阶段名> 180

# ④ 回归：确认没把已有功能改坏
bash scripts/22-macos-run-test.sh smoke 180
```

**注意 ① 只需在「源码有改动」后执行**：initramfs 里打包了全部阶段脚本，
运行时用内核命令行参数 `test=<阶段名>` 选择要跑哪个（由 `22-macos-run-test.sh` 自动传入），
所以同一份产物可以依次跑多个阶段的测试，不需要为每个阶段都重建。

> 启动日志里会出现一行 `Unknown kernel command line parameters "test=xxx"`：
> 这是内核对我们自定义参数的正常提示（`pr_warn`，不带 `WARNING:` 前缀，不会命中告警检查项），
> 属于预期噪声，不是错误。

**产物位置**：`artifacts/`（内核与 initramfs）、`logs/`（每次 QEMU 串口日志，带时间戳）。

## 四、测试协议（必须遵守）

### 4.1 检查项标记格式

阶段测试脚本运行在 QEMU 里（busybox sh），通过 `source /tests/lib.sh` 提供的函数输出：

```
[CHECK:PASS] <检查项名称>
[CHECK:FAIL] <检查项名称> -- <原因>
[TEST:START] <阶段名>
[TEST:END]   <阶段名> pass=N fail=M
```

`scripts/22-macos-run-test.sh` 靠解析这些标记给出结论，**任何没有标记的输出都不算验证**。

### 4.2 可用的断言函数（tests/runner/lib.sh）

| 函数 | 用途 |
|---|---|
| `pass "名称"` / `fail "名称" "原因"` | 手动判定 |
| `check_exists "名称" /path` | 路径存在（设备节点、sysfs/debugfs 文件） |
| `check_contains "名称" 文件 "子串"` | 文件内容包含 |
| `check_not_contains "名称" 文件 "子串"` | 文件内容不包含 |
| `check_eq "名称" 期望 实际` | 字符串相等 |
| `check_true "名称" 期望 实际` | 同 check_eq（语义化写法） |
| `check_gt "名称" 实际 阈值` | 整数大于 |
| `check_nonempty "名称" 值` | 非空 |
| `check_cmd "名称" 命令...` | 命令退出码为 0 |
| `info "文字"` | 仅打印，不计入检查 |

### 4.3 测试脚本要求

- 路径：`tests/phases/<阶段名>.sh`（如 `tests/phases/01-io-models.sh`）。
- 开头注释说明：本阶段验证什么、为什么这样验证。
- 每个检查项名称要**能当结论读**（例如"epoll 在 2 秒内报告 EPOLLIN"而不是"检查1"）。
- 关键检查要打印实际观测值，便于事后从日志复查（`info` 或写进检查项名称里）。
- 模块加载顺序可在 `tests/phases/<阶段名>.modules` 覆盖（默认用 `driver/modules.load`）。

### 4.4 用户态测试程序

- 路径：`user/*.c`（会被自动编译成静态 aarch64 程序并放进 initramfs 的 `/bin/`）。
- 建议"程序负责打印事实，脚本负责判定"，但程序自身的失败也要用退出码表达。
- 允许 include 驱动目录头文件（编译时带 `-I driver`）。

## 五、验证门槛（Definition of Done）

一个阶段**只有同时满足以下五条才算完成**：

1. `make` 无 error、无 warning（新增代码部分）；
2. `bash scripts/22-macos-run-test.sh <本阶段>` 全部检查项 PASS 且跑到 `[TEST:END]`；
3. `bash scripts/22-macos-run-test.sh smoke` 仍然全部 PASS（回归未破）；
4. 日志里 `内核 panic: 0`；出现 `WARNING/BUG/Call trace` 必须在文档里解释清楚（要么修掉，要么说明为何是预期）；
5. 三份文档已落盘（见第六节），且**文档里的结论必须能被日志复现**（写清日志文件名）。

---

## 六、文档产出规范

每阶段产出三份文档，路径固定：

| 文档 | 路径 | 内容要求 |
|---|---|---|
| 实现记录 | `docs/impl/<阶段名>-实现记录.md` | 改了什么文件、每个函数为什么这么写、内核 API 的作用、遇到的问题与解决过程、验证命令与结论（附日志文件名） |
| 知识点 | `docs/kb/<阶段名>-知识点.md` | 面向"面试与被追问"：机制原理、数据结构、内核源码位置、边界与坑、常见面试问法与答法 |
| 验证报告 | `docs/verify/<阶段名>-验证报告.md` | 由**独立验证者**写：检查项表格（名称/预期/实测/证据行号）、遗留疑点、是否满足 DoD |

文档风格：
- 中文，代码/命令用 ``` 代码块；
- **不要写"应该""大概"**，写实测结果与日志证据；
- 引用内核源码时给出 `文件:行号`（如 `drivers/iio/industrialio-buffer.c:1234`）。

## 七、编码规范（驱动侧）

1. 沿用现有 `sensor_char.c` 风格：`/* ... */` 中文注释解释**为什么**，而不是重复代码在做什么。
2. 新增内核 API 使用处必须有一行注释说明其作用与上下文约束（能否睡眠、持有什么锁）。
3. 日志用 `dev_info/dev_err(&sd->client->dev, ...)`，禁止用裸 `printk`（模块 load/unload 除外）。
4. 锁的粒度：`sd->lock`(mutex) 保护 `latest/stats` 与 I2C 访问；中断上下文不得获取可能睡眠的锁。
5. 所有 `copy_to_user/copy_from_user` 失败必须返回正确 errno。
6. 新增文件必须加入 `driver/Makefile` 与 `driver/modules.load`（或阶段级 `.modules`）。
7. 不允许破坏已有 ioctl 的 ABI（`driver/sensor_ioctl.h` 里已有命令号保持兼容，只能新增）。

## 七点五、实验纪律：负控实验必须在隔离副本里做（血泪教训）

**规则：交付工作树（worktree）里绝不允许做破坏性/负控实验。**三选一：
1. 复制 `driver/` 到 `/tmp/nc-xxx/` 改副本，用 `PROJ=/tmp/nc-xxx` 或 `LAB=/tmp/nc-xxx` 构建；
2. `git worktree add /tmp/nc-xxx <commit>` 另开一棵树；
3. 至少在实验后用 `git checkout -- <file>` 还原，并且**逐个文件比对 sha256**。

违反这条会产出两类"看起来全绿其实错误"的成果：

| 事故 | 经过 | 后果 | 靠什么发现 |
|---|---|---|---|
| 阶段 05 | 实现者在交付树里做完负控（`trigger_handler` 温/湿度通道互换，带 `NEGCTRL-B` 标记）未还原就汇报全绿 | 交付源码**开箱即 19 PASS / 3 FAIL** | 独立验证者重建后复现 |
| 阶段 06 | 验证者在交付树里做负控（去掉周期上界校验、`ring_capacity` 返回固定值），编辑器报错但其实文件已被写入 | 残留 `/* NC-... */` 改动 | 集成负责人全树扫描 |

**注意**：新交付的文件常是**未跟踪文件（untracked）**，`git status` 只显示"有新文件"，
看不到内容被改过——所以"git 是干净的"**不能**证明交付文件没被污染。

**合并门禁**：`bash scripts/23-check-worktree-clean.sh [项目目录]`
（扫描代码文件里的 `NC-`/`NEGCTRL`/`EXPERIMENT` 标记、注释掉的关键语句、以及未跟踪文件的 sha256）。

## 八、禁止事项（会造成结论不可信）

1. **禁止修改内核源码树**（`~/kernel-build/linux-6.6.156` 与宿主 `kernel-src/`），
   除已存档的 glibc 兼容补丁（`artifacts/logs/0001-host-tools-newer-glibc.patch`）之外。
2. **禁止跳过 smoke 回归**，或为了让测试过而放宽检查项。
3. **禁止伪造/推测验证结果**：没跑过就写"通过"属于严重错误；测试失败时如实记录并继续修。
4. **禁止把 `[CHECK:PASS]` 直接写死在测试脚本里**（等于自欺欺人）。
5. 禁止绕过 `scripts/13/21/22` 三个脚本自己拼命令跑 QEMU（会导致产物与日志不一致，
   破坏可复现性）；确有必要时先说明理由并把等价命令写进文档。

## 九、已知坑（都已踩过，别再踩）

| 现象 | 根因 | 处理 |
|---|---|---|
| 内核编译报 `Syntax error: word unexpected` | 宿主源码树混入 macOS 的 Mach-O 产物（`scripts/kconfig/conf`） | 从官方 tarball 重新解出（scripts/11） |
| `unknown type name 'uuid_t'` | 树里 `scripts/mod/file2alias.c` 被改成 `k_uuid_t`，与官方不一致 | 用官方 tarball 重建（scripts/11） |
| `redefinition of 'struct list_head'` | Ubuntu 26.04 的 glibc 2.43 让 `<sys/stat.h>` 拉进 `/usr/include/linux/stat.h` → `<linux/types.h>` → `tools/include/linux/types.h` | 双头文件加同名 include guard（见补丁文件） |
| 宿主工具编译报结构体成员错误 | 虚拟机默认 gcc 15 过新（内核 6.6 支持到 gcc 13） | 显式 `CC=gcc-13 HOSTCC=gcc-13` |
| ftrace 写入后 QEMU 卡死 | `-accel hvf -cpu host` 与 ftrace 冲突 | 固定用 `-accel tcg -cpu cortex-a72` |
| 设备树 `Properties must precede subnodes` | 节点插到了根节点属性中间 | 插到根节点闭合括号之前（scripts/20） |
| 模块加载失败 `invalid module format` | 模块与 Image 版本/配置不一致 | 永远用同一棵内核树编模块，并刷新 `artifacts/Image` |
