# 01 - 环境搭建与踩坑实录

> 本文记录本项目环境从零搭起来过程中**真实遇到并解决**的问题。
> 这些坑本身就是"问题定位方法"的最好素材：每条都写明 现象 → 原因 → 解决。

## 1. 架构决策：为什么必须有一台 Linux 虚拟机

**现象**：想在 macOS 上 `insmod sensor_char.ko`。
**原因**：内核模块是加载进 **Linux 内核** 的代码；macOS 的 XNU 内核不认 `.ko`。
**结论**：模块必须在一个 Linux 内核里运行。三种选择：

| 方案 | 成本 | 真实度 | 本项目选择 |
|------|------|--------|-----------|
| 真实 ARM 开发板 | ¥100–400 + 快递 | 100% | 进阶（见 docs/04） |
| QEMU 模拟 ARM 板 | 0 | 95%（CPU/内存/中断/I2C 全模拟） | ✅ 主线 |
| Docker 容器 | 0 | ❌ 容器内不能 insmod（内核是宿主的） | 不适用 |

但 **QEMU 在哪跑？** macOS 上没有 Linux 编译环境（编内核需要 host gcc/glibc 一整条链），
所以再加一台 Lima 虚拟机作为"Linux 构建机"，QEMU 放在里面跑。

## 2. 坑：Homebrew 下载失败（中国网络）

**现象**
```
Error: Failed to download resource "ca-certificates"
curl: (35) LibreSSL SSL_connect: SSL_ERROR_SYSCALL in connection to ghcr.io:443
```
**原因**：Homebrew 的二进制包（bottle）托管在 ghcr.io，国内直连不稳定。
**解决**：换清华镜像
```bash
export HOMEBREW_BOTTLE_DOMAIN=https://mirrors.tuna.tsinghua.edu.cn/homebrew-bottles
export HOMEBREW_API_DOMAIN=https://mirrors.tuna.tsinghua.edu.cn/homebrew-bottles/api
brew install qemu ...
```

同理，虚拟机里 apt 走宿主代理时也可能 502：
```
E: Failed to fetch http://archive.ubuntu.com/... 502 Bad Gateway
```
**解决**：虚拟机内换清华 apt 源（`scripts/02-setup-vm.sh` 已自动化）。

## 3. 坑：macOS 自带 make 版本太老

**现象**
```
Makefile:15: *** GNU Make >= 3.82 is required. Your Make version is 3.81.  Stop.
```
**原因**：macOS 20 年没更新过 `/usr/bin/make`（GPLv3 原因）。
**解决**
```bash
brew install make
export PATH="/opt/homebrew/opt/make/libexec/gnubin:$PATH"   # 让 make 指向 4.4.1
```
`gnubin` 目录里是**以标准名命名的软链**（`make` 而不是 `gmake`）。

## 4. 坑：内核 host 工具找不到 `elf.h`（macOS 没有 Linux 头）

**现象**（在 macOS 上直接编内核时）
```
scripts/sorttable.c:27:10: fatal error: 'elf.h' file not found
```
**原因**：内核构建过程要编一批**宿主工具**（`sorttable`、`mk_elfconfig`、`modpost`），
它们 include Linux 的 `<elf.h>`；macOS SDK 不提供。

**解决（正确姿势）**：**只给需要的目标加 include 路径，不要用全局 CPATH！**
```makefile
# scripts/mod/Makefile
KBUILD_HOSTCFLAGS += -I$(srctree)/tools/include   # 并把 musl 的 elf.h 放进 tools/include/
```
注意：`hostc_flags` 用的是 `KBUILD_HOSTCFLAGS`，**不是** `HOSTCFLAGS`——加错变量不生效（我在这上面浪费了一轮）。

---

## 5. 坑：全局 `CPATH` 污染宿主程序编译

**现象**
```
"_stdin", referenced from: _main in mk_elfconfig.o
ld: symbol(s) not found for architecture arm64
```
**原因**：为了上一条的 `elf.h`，我用 `export CPATH=<musl sysroot>/include` 全局指路。
结果 host 程序编译时 include 到了 **musl 的 `stdio.h`**（`stdin` 是 `extern FILE *stdin`），
而链接的是 macOS libc（`stdin` 是宏 `__stdinp`）→ 符号对不上。
**教训**：交叉工具链的 sysroot **绝不能用 CPATH 全局暴露**，只能按目标精确添加 `-I`。

---

## 6. 坑：`sorttable` 链接 `-lpthread` 在 macOS 上必然失败

**现象**
```
ld: symbol(s) not found for architecture arm64
make[2]: *** [scripts/Makefile.host:114: scripts/sorttable] Error 1
```
**原因**：`HOSTLDLIBS_sorttable = -lpthread`；macOS 没有 `libpthread`（pthread 合进 libSystem）。
**解决**：arm64 上 `BUILDTIME_TABLE_SORT` 只是**构建期异常表排序优化**，对驱动开发无影响，
注释掉 `arch/arm64/Kconfig` 里的 `select BUILDTIME_TABLE_SORT` 即可绕过。
（注意：BSD `sed` 不支持 `\s`，要用 `perl -pi -e` 或 `[[:space:]]`。）

## 7. 坑：`uuid_t` 与 macOS SDK 冲突

**现象**
```
file2alias.c:45:3: error: typedef redefinition with different types
      ('struct uuid_t' vs '__darwin_uuid_t' (aka 'unsigned char[16]'))
```
**原因**：`scripts/mod/file2alias.c` 自己 `typedef struct { __u8 b[16]; } uuid_t;`，
而 macOS SDK 的 `<sys/types.h>` 也定义了 `uuid_t`。
**错误尝试**：`-Duuid_t=mod_uuid_t` —— 宏会把**系统头里的同名 typedef 也改掉**，冲突依旧（只是换了名字）。
**解决**：直接把 `file2alias.c` 里的类型名改成 `k_uuid_t`（仅构建期工具，安全）。

## 8. 坑：macOS 构建残留（Mach-O）在 Linux 里被执行

**现象**
```
scripts/kconfig/conf: 3: Syntax error: word unexpected (expecting ")")
```
**原因**：先在 macOS 编了一半，`scripts/kconfig/conf` 是 **Mach-O 可执行文件**；
拷到 Linux 后 `make clean` 没清掉它，Linux 试图把它当脚本执行。
**解决**
```bash
find . -type f -print0 | xargs -0 file | grep "Mach-O" | cut -d: -f1 | while read f; do rm -f "$f"; done
```
**结论**：**不要跨平台混编同一棵内核源码树**。本项目最终把构建完全放在 Linux VM 里做。

## 9. 坑：Lima 挂载的 `$HOME` 是只读的

**现象**
```
rm: cannot remove './scripts/kconfig/conf': Read-only file system
bash: .../project/.writetest: Operation not permitted      # 实测两种报错都会出现
```
**原因**：Lima 出于安全，mount 默认 `writable: false`（`~/.lima/dev/lima.yaml` 里 mounts 只有 `- location: "~"`，
没有 `writable: true`）。注意 `mount` 命令在虚拟机里显示的是 `virtiofs (rw)`——**标志位是 rw，但实际写入被宿主侧拒绝**，
所以不能只看 mount 输出判断，要实际 `touch` 一下。
**解决**（本项目采用）：**构建放虚拟机本地盘**，只读挂载只用来读源码：
```bash
cp -a /Users/lucien/.../linux-6.6.156 ~/kernel-build/   # 40 秒
# 构建完成后把产物拷回宿主
limactl cp dev:/home/lucien.guest/virt-sensor.dtb artifacts/
```
（若要开启可写：`limactl edit dev` → 给 mount 加 `writable: true` → 重启 VM。本项目故意保持只读，避免误改宿主源码。）

## 10. 验证环境是否可用（三连测）

```bash
# 1) 交叉工具链能产出 ARM64 用户态程序
aarch64-linux-musl-gcc -static -O2 -o /tmp/t user/sensor_test.c && file /tmp/t
# 期望：ELF 64-bit LSB executable, ARM aarch64, statically linked

# 2) 虚拟机内能编内核
limactl shell dev -- make -C ~/kernel-build/linux-6.6.156 -j4 Image
# 期望：arch/arm64/boot/Image 约 40MB

# 3) QEMU 能启动 ARM64 Linux
bash scripts/04-run-qemu-vm.sh
# 期望：=== [1] BOOT: 6.6.156 / aarch64 ===
```

## 11. 交付结论

- **编译内核/模块 → Linux 虚拟机（native）**：零坑，10–30 分钟一次全量。
- **交叉编译用户态程序 → macOS 上 musl 工具链**：真正体现"搭建交叉编译工具链"。
- **运行/调试 → QEMU**：秒级重启，GDB 可直连 CPU，适合一天内反复迭代。
- macOS 直编内核的各种坑（第 4–8 条）已完整记录，作为"宿主环境差异导致构建失败"的定位范例。
