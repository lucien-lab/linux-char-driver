## 一、dmesg：第一现场

### 1.1 驱动里的打印分级（写代码时就要规划）

```c
dev_err(dev,  "...\n");    /* 错误：一定要有，方便报错定位 */
dev_warn(dev, "...\n");    /* 警告：可恢复的异常 */
dev_info(dev, "...\n");    /* 关键流程：probe 成功、参数解析结果 */
dev_dbg(dev,  "...\n");    /* 调试细节：默认不打印，可用于生产环境 */
```
`probe()` 里应打印"我从设备树读到了什么"，这一条能省掉大量猜测：

```
sensor_char sensor-char: DT: i2c-bus=0 sensor-addr=0x48 interval=500ms
sensor_char sensor-char: i2c client on bus 0 addr 0x48
sensor_char sensor-char: irq registered: virq=21
sensor_char sensor-char: probe done: major=511 minor=0 /dev/sensor0
```

### 1.2 常用命令

```bash
dmesg | tail -30                    # 最近的内核日志
dmesg -w                            # 实时跟踪（调试时开着）
dmesg | grep -i sensor              # 只看自己驱动的
dmesg -l err,warn                   # 只看错误和警告
dmesg | grep -c "Call trace"        # 有没有内核崩溃/告警
```

### 1.3 动态调试（不用改代码就能打印 dev_dbg）

```bash
mount -t debugfs none /sys/kernel/debug
echo 'file sensor_char.c +p' > /sys/kernel/debug/dynamic_debug/control
cat /dev/sensor0                    # 现在会看到 dev_dbg 的输出
```

## 二、ftrace：看清"代码真的执行了吗、执行了多少次"

**本项目实测**：验证线程化中断下半部是否真在跑、跑多快。

```bash
mount -t debugfs none /sys/kernel/debug
cd /sys/kernel/debug/tracing

echo 0 > tracing_on                        # 先关，避免半截数据
echo function > current_tracer             # 函数级追踪
echo sensor_irq_thread > set_ftrace_filter # 只追踪我关心的函数
echo 1 > tracing_on
sleep 2
echo 0 > tracing_on
cat trace | tail -5
```

**实测输出**（这是本项目的核心证据：中断线程每 ~500ms 真实执行一次）：
```
#           TASK-PID     CPU#  |||||  TIMESTAMP  FUNCTION
 irq/21-sensor_c-59  [000] .....  1.782342: sensor_irq_thread <-irq_thread_fn
 irq/21-sensor_c-59  [000] .....  2.276037: sensor_irq_thread <-irq_thread_fn
 irq/21-sensor_c-59  [000] .....  2.777669: sensor_irq_thread <-irq_thread_fn
 irq/21-sensor_c-59  [000] .....  3.279062: sensor_irq_thread <-irq_thread_fn
```
从输出能直接读出三件事：
1. **执行者是内核线程** `irq/21-sensor_c`（证明 request_threaded_irq 生效，不是硬中断直接跑）；
2. **调用者是** `irq_thread_fn`（内核中断线程框架）；
3. **周期 ≈ 0.494–0.501s**（证明 hrtimer 的 500ms 生效）。

### 2.1 其他常用玩法

```bash
# 看调用链（谁调用了我的函数）
echo function_graph > current_tracer
echo sensor_irq_thread > set_graph_function

# 看函数耗时
echo function_graph > current_tracer
cat trace | head -40

# 追踪中断事件（第几次中断、哪个 CPU）
echo 1 > events/irq/irq_handler_entry/enable
echo 1 > events/irq/irq_handler_exit/enable

# 清空过滤器（注意：不能 echo 0，要空写）
echo > set_ftrace_filter
echo nop > current_tracer
```

### 2.2 ftrace 的定位价值

| 现象 | ftrace 能回答 |
|------|--------------|
| read() 一直阻塞不返回 | `sensor_irq_thread` 一次都没执行 → 触发源没工作 |
| 数据不更新 | 中断在跑但 `i2c_smbus_read_word_data` 失败 → 看 `events/i2c` 或函数返回值 |
| 周期不对 | 两次 `sensor_irq_thread` 的时间差 ≠ 配置周期 → hrtimer 参数没生效 |
| 性能异常 | function_graph 找出耗时最长的函数 |

## 三、GDB：单步、看变量、看调用栈

**本项目实测**（`scripts/05-debug-gdb.sh`）：

```bash
# 终端 1：QEMU 暂停启动，开放 gdbstub:1234
qemu-system-aarch64 -M virt -cpu cortex-a72 -m 1G -display none -serial stdio \
  -dtb ~/virt-sensor.dtb -kernel ~/kernel-build/linux-6.6.156/arch/arm64/boot/Image \
  -initrd ~/initramfs.cpio.gz -append "console=ttyAMA0 nokaslr" -S -s

# 终端 2：GDB 连接并下断点
gdb-multiarch ~/kernel-build/linux-6.6.156/vmlinux
(gdb) target remote :1234
(gdb) break i2c_get_adapter
(gdb) continue
```

**实测输出**（断点正好命中我们驱动 probe 里调用的 I2C 子系统函数）：
```
Breakpoint 1, i2c_get_adapter (nr=0) at drivers/i2c/i2c-core-base.c:2642
2642		mutex_lock(&core_lock);
#0  i2c_get_adapter (nr=0) at drivers/i2c/i2c-core-base.c:2642
#1  0xffff80007a7bc744 in ?? ()      <- 这两帧是驱动模块（没有符号，所以显示 ??）
#2  0xffff80007a7bf1c0 in ?? ()
pc 0xffff800080e91e70  <i2c_get_adapter+8>
```

### 3.1 关键技巧：给内核模块加符号

内核模块是运行时加载的，GDB 不知道它的加载地址，所以上面显示 `??`：

```bash
# 在 guest 里加载模块后，取得它的 .text 段地址
insmod /lib/modules/6.6.156/sensor_char.ko
cat /sys/module/sensor_char/sections/.text     # 例如 0xffff8000801a0000

# GDB 里注册模块符号
(gdb) add-symbol-file ~/lab/driver/sensor_char.ko 0xffff8000801a0000
(gdb) break sensor_irq_thread      # 现在就能断在模块函数里
(gdb) continue
(gdb) bt                           # 确认是内核中断线程调用进来的
(gdb) p sd->latest.temp_milli      # 直接读驱动内部数据结构
(gdb) next / step / finish         # 单步
```

### 3.2 GDB 定位价值

| 现象 | GDB 能回答 |
|------|-----------|
| probe 没进 | `break sensor_probe` 没命中 → DT 没匹配 / 驱动没注册 |
| 数据不对 | `p sd->latest`、`p raw` 看寄存器原始值和解析结果 |
| 崩溃/Oops | 用 Oops 里的 `pc` 地址 + `list *0xffff...` 定位到源码行 |
| 锁死 | `info threads`、`thread apply all bt` 看谁持有锁 |

### 3.3 注意事项

- **必须加 `nokaslr`**：否则运行时地址与 vmlinux 符号地址不一致，断点会打偏。
- 模块卸载后符号失效，重新 insmod 后要重新 `add-symbol-file`。
- `-S -s` 会暂停 CPU，别忘了 `(gdb) continue`。
- 硬件断点数量有限（4 个左右），断点多了会失败，改用软件断点或删掉不用的。

## 四、真实案例复盘

### 案例 1：内核 WARNING "handler enabled interrupts"（本项目真实遇到并修复）

**现象**：用户态 `write(fd, "\x01", 1)` 手动触发采样时，内核打印警告：

```
------------[ cut here ]------------
irq 21 handler sensor_irq_hard+0x0/0x28 [sensor_char] enabled interrupts
WARNING: CPU: 0 PID: 65 at kernel/irq/handle.c:161 __handle_irq_event_percpu+0x204/0x238
Modules linked in: sensor_char(O) i2c_stub
CPU: 0 PID: 65 Comm: sensor_test Tainted: G           O       6.6.156 #2
```

**定位过程**
1. 看 `PID: 65 Comm: sensor_test` → 这是**进程上下文**（用户态程序在跑 write），不是中断上下文。
2. 看告警文本 `handler ... enabled interrupts` → 内核在中断处理流程里检测到"中断处理程序把中断打开了"。
3. 回看驱动：`write()` 里直接调用
   ```c
   generic_handle_domain_irq(sd->irq_domain, 0);
   ```
   而真实中断发生时 CPU 会自动关中断（`irqs_disabled()==true`），
   进程上下文里中断是开的，内核的 `__irq_enter` / `__irq_exit` 状态机因此报错。
   → **根因：触发虚拟中断时没有模拟中断上下文。**

**修复**
```c
local_irq_disable();
generic_handle_domain_irq(sd->irq_domain, 0);
local_irq_enable();
```

**验证**：重编重跑，`dmesg | grep -c 'WARNING\|Call trace'` 输出 **0**（修复前是 1）。
> 附带发现：hrtimer 回调里触发不需要这么做——因为 softirq 上下文本来就关中断。
> 这个案例把"上下文（process/softirq/hardirq）"这个抽象概念变成了可见的行为差异。

### 案例 2：驱动加载失败——六种常见原因速查表

按**发生概率从高到低**排查（本项目前 4 条都实测过）：

| # | 现象（dmesg / insmod 输出） | 原因 | 定位方法 | 修复 |
|---|----------------------------|------|---------|------|
| 1 | `unknown symbol xxx (err -2)` | 用了未导出（或未编入内核）的符号 | `grep xxx Module.symvers`；`nm vmlinux \| grep xxx` | 换 API / 打开对应 `CONFIG_*`（本项目 irq_sim 就这样，最终改为自建 irq_domain） |
| 2 | `invalid module format` / `version magic ... should be` | 模块与内核版本/配置不一致 | `modinfo sensor_char.ko \| grep vermagic`；`uname -r` | 用**同一个内核树**编译模块（`make KDIR=<内核源码>`） |
| 3 | `insmod: can't insert: Invalid argument` | 模块参数错、probe 返回错误 | `dmesg \| tail`（probe 里的 `dev_err` 是关键） | 看驱动自己打印的错误码 |
| 4 | 加载成功但 `/dev/sensor0` 不存在 | DT 没匹配上 → probe 没跑 | `dmesg \| grep sensor`；`ls /sys/bus/platform/drivers/sensor_char/` | 检查 `compatible` 拼写、`.of_match_table`、`MODULE_DEVICE_TABLE(of,...)`、dtb 是否真的传给了 QEMU（`-dtb`） |
| 5 | `probe` 打印 `-EPROBE_DEFER` 一直重试 | 依赖（I2C 总线）还没就绪 | `dmesg \| grep defer` | 先 `insmod i2c-stub.ko` 再加载驱动；真机上检查控制器驱动是否编入内核 |
| 6 | `Operation not permitted` / `Permission denied` | 权限或内核锁 | `id`；`dmesg \| grep -i lockdown` | `sudo insmod`；检查 Secure Boot / lockdown |

**本项目实测案例 2 的一次真实过程**（第 1 条）：
```
ERROR: modpost: "devm_irq_domain_create_sim" [sensor_char.ko] undefined!
```
→ 用 `grep irq_domain_create_sim Module.symvers` 发现只有 `irq_domain_create_simple`（另一个函数），
说明 `CONFIG_IRQ_SIM` 根本没编进这棵内核 → 改为驱动内部自建 `irq_domain`，不依赖该配置。

### 案例 3：数据异常（读到的值不合理）

| 现象 | 可能原因 | 定位方法 |
|------|---------|---------|
| 读回 `-ENXIO`/`-EREMOTEIO` | 从设备地址错 / 无 ACK | `i2cdetect -y 0` 看地址是否存在；`i2cget -y 0 0x48 0x00 w` 用户态直读 |
| 值恒定不变 | 传感器没在转换 / 读的寄存器错 | 用 `i2cget` 在用户态读同一寄存器对比 |
| 值大 256 倍或符号错 | 字节序 / 有符号当无符号 | 打印原始 `raw`（`dev_dbg`），手工换算验证公式 |
| 偶尔读失败 | 多进程并发 / 缺锁 | 检查是否所有 I2C 访问都在 `mutex` 保护下 |
| 数据跳变 | 触发频率与采样率不匹配 | ftrace 看两次中断间隔，对比 ioctl 设置的周期 |

**本项目验证数据链路正确的方法**（用户态与内核态互证）：
```bash
# 内核驱动读 0x00 -> 25.412C
cat /dev/sensor0
# 用户态 i2c-tools 直接读同一寄存器（绕过驱动）
i2cget -y 0 0x48 0x00 w      # 应得到相近的原始值
```

## 五、方法论：从现象到根因的固定排查顺序

```
1. 看现象在哪一层
   ├─ insmod 失败            → 模块加载层（版本/符号/参数）
   ├─ 加载成功但设备没出现    → 设备树匹配 / probe
   ├─ 设备在但 open 失败      → 权限 / 设备号 / cdev 注册
   ├─ open 成功但 read 阻塞   → 数据源（中断/定时器）没工作  → ftrace
   └─ 数据不对               → I2C 通信 / 解析公式           → i2c-tools 互证
2. 每个判断都用"可观测证据"支撑
   dmesg（发生了吗）→ ftrace（代码执行了吗/几次/多快）→ GDB（变量到底是什么）
3. 一次只改一个变量，改完立刻验证（本项目 WARNING 修复就是这么闭环的）
4. 把结论写回文档（本文就是产物）
```
